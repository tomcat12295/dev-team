# /review-plan - 計画レビュー

## 手順

1. memberから計画（submit_plan）を受信
2. 以下の観点でレビュー
3. `approve_plan(task_id)` または `reject_plan(task_id, reason, feedback)`

## 1. タスク理解（summary）

- memberがタスクの目的を正しく理解しているか？
- 受け入れ条件の解釈にズレはないか？
- スコープの認識が合っているか？（やりすぎ・足りなさの両方を確認）

**却下例**: 「認証トークンの検証を実装」というタスクで、トークン発行まで計画に含めている

## 2. 実装方針（approach）

### 設計判断
- なぜその方法を選んだか理由があるか？（「なんとなく」は却下）
- 既存コードのパターンと一貫しているか？（新しいパターンの導入に正当な理由があるか）
- 責務の分離は適切か？（1つの関数/クラスに詰め込みすぎていないか）

### 変更の影響
- 変更が他のモジュールに波及しないか？（波及するなら、その対応が計画に含まれているか）
- 既存のテストが壊れる可能性はないか？
- 破壊的変更を含む場合、移行パスは考慮されているか？

### よくある問題
- 過剰設計: 今必要ない抽象化やインターフェースを入れようとしていないか
- 過少設計: 明らかに必要な考慮（エラー処理、並行性等）が抜けていないか
- 車輪の再発明: 既存のユーティリティやライブラリで解決できないか

## 3. 変更ファイル（files_to_change / files_to_create）

- allowed_files の範囲内か？
- 不要なファイル変更が含まれていないか？（ついでリファクタ禁止）
- 新規ファイル作成は本当に必要か？既存ファイルに追加で済まないか？
- ファイル名・配置場所は既存の構造と一貫しているか？

## 4. テスト計画（test_plan）

- テストケースが受け入れ条件を網羅しているか？（1条件につき最低1テスト）
- 正常系だけでなく異常系が含まれているか？
- 境界値テストが必要な箇所で計画されているか？
- TDDで実装する前提になっているか？（テスト→実装の順序が明記されているか）
- モックの方針は妥当か？（過剰モックで実質テストになっていないケースに注意）

## 5. モデリング・I/F

- データ構造の設計が記載されているか？（型定義、フィールド名等）
- 他モジュールとのI/Fが明確か？（引数・戻り値・例外）
- 命名が既存コードと一貫しているか？

## 却下時

具体的に書くこと:
- **何が問題か**: 「設計が不適切」ではなく「XxxクラスにYyyの責務まで持たせている」
- **どう直すか**: 「見直してください」ではなく「ZzzServiceに分離して、Xxxからは呼び出すだけにする」
- **参考先**: 既存コードで同様のパターンがあればファイルパスを示す
