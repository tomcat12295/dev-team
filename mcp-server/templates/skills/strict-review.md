# /strict-review - テストファーストレビュー

## ワークフロー

```
1. 計画レビュー → approve_plan
   ↓
2. memberがテストコードのみ実装
   ↓
3. テストレビュー依頼を受信（submit_test）
   ↓
4. テストをレビュー → approve_test / reject_test
   ↓
5. 承認後、memberが実装コードを書く
   ↓
6. コードレビュー（/review-code 参照）→ PMに報告
```

## テストレビュー

### ツール
- 承認: `approve_test(task_id, comments?)`  → phaseが自動的に `implementing` に更新
- 却下: `reject_test(task_id, reason, feedback)`

### レビューの進め方

1. **受け入れ条件を手元に用意**する（assign_taskの内容を確認）
2. テストファイルを**全て読む**
3. 受け入れ条件とテストケースを**1対1で突き合わせる**
4. 以下の観点で検証
5. 問題がなければ承認、あれば却下

## テストレビュー観点

### 1. 受け入れ条件との対応

最重要。受け入れ条件に対応するテストが1つもなければ即却下。

- 各受け入れ条件に対して、それを検証するテストが**明確に**存在するか？
- テストの期待値が受け入れ条件の意図と合っているか？
- 受け入れ条件に書かれていないが**暗黙に必要な**テストはないか？（例: 「ユーザーを作成できる」には重複チェックも必要）

### 2. 異常系・エッジケース

正常系だけのテストは却下。最低限以下を確認:

- **不正入力**: null, undefined, 空文字列, 型違い
- **境界値**: 0, 1, 最大値, 最小値, 上限ちょうど, 上限+1
- **状態異常**: 存在しないID, 権限なし, 重複, 競合
- **外部エラー**: I/O失敗, タイムアウト, ネットワークエラー（該当する場合）

### 3. テスト設計の品質

- **テスト名**: `it('should...')` ではなく、入力条件と期待結果が名前から分かるか？
  - NG: `it('works correctly')`
  - OK: `it('returns 404 when user ID does not exist')`
- **独立性**: テスト間に実行順序の依存がないか？共有状態を変更していないか？
- **Arrange-Act-Assert**: 各テストが「準備→実行→検証」の構造になっているか？
- **1テスト1関心事**: 1つのテストで複数の無関係な振る舞いを検証していないか？

### 4. モックの妥当性

- モック対象は外部I/O（ファイル、DB、API）に限定されているか？
- ビジネスロジックをモックしていないか？（ロジックをモックしたテストは何も検証していない）
- モックの戻り値は現実的か？（実際のAPIレスポンスと乖離していないか）
- モックのリセット（beforeEach/afterEach）は適切か？

### 5. 実行可能性

- テストが**現時点で実行可能**か？（未実装の関数をimportしていてコンパイルエラーにならないか）
- テストが**失敗する**ことを確認したか？（Green状態のテストはTDDになっていない）

## 却下時

具体的に指摘する:
- **不足しているテストケース**: 「異常系が足りない」ではなく「ユーザーIDが空文字列の場合のテストがない」
- **設計の問題**: 「可読性が低い」ではなく「テスト名からは正常系と異常系の区別がつかない。describeブロックで分けること」
- **修正後の期待**: 修正したら何が追加/変更されるべきかを明記
