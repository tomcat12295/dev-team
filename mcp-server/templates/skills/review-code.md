# /review-code - コードレビュー

## 手順

1. memberから完了報告を受信
2. 変更ファイルを**全て読む**（差分だけでなくファイル全体の文脈を把握）
3. 問題があればmemberに差し戻し、なければPMに報告

**レビューなしでPM報告は禁止。妥協せずに詰める。**

## 1. 要件充足

- 受け入れ条件を**1つずつ**確認。全て満たしているか？
- 部分実装になっていないか？（「とりあえず動く」で済ませていないか）
- 受け入れ条件以外の余計な変更が入っていないか？

## 2. TDD確認

- テストが書かれているか？（テストなしの実装は即却下）
- テストが全てパスしているか？（結果を報告に含めているか）
- テストが実装の詳細に依存しすぎていないか？（リファクタで壊れるテストは脆い）

## 3. テスト品質

### 網羅性
- 受け入れ条件ごとにテストがあるか？
- 正常系: 代表的な入力パターンをカバーしているか？
- 異常系: 不正入力、null/undefined、空文字列、権限エラー等
- 境界値: 0/1/max、空配列/1要素/多数要素、文字列長の上限等

### テスト設計
- テスト名から「何を」「どういう条件で」「どうなるか」が読み取れるか？
- 1テスト1アサーションの原則に近いか？（複数アサーションで何が失敗か分からないテストは改善）
- テスト間に依存がないか？（実行順序に依存するテストは禁止）
- モックが適切か？（外部I/Oのみモック。ロジックをモックして「テストした気」になっていないか）

## 4. コード品質

### 設計
- 責務が明確に分離されているか？（1関数1責務）
- 関数が長すぎないか？（目安: 30行以上は分割を検討）
- ネストが深すぎないか？（3段以上は早期リターン等で平坦化）
- 重複コードがないか？（3箇所以上の重複は共通化を検討）

### 命名
- 変数名・関数名が意図を表しているか？（`data`, `tmp`, `result`等の曖昧な名前は却下）
- bool変数は `is`/`has`/`can`/`should` で始まっているか？
- 既存コードの命名パターンと一貫しているか？

### エラー処理
- 外部入力（ユーザー入力、API応答、ファイルI/O）のバリデーションがあるか？
- エラーが握りつぶされていないか？（空catch、ログだけで処理続行等）
- エラーメッセージが原因特定に役立つ内容か？（「エラーが発生しました」は不可）
- 内部コード間の防御的プログラミングが過剰でないか？（型システムで保証されるものを再チェックしていないか）

### セキュリティ
- ユーザー入力がサニタイズされているか？
- SQLインジェクション、XSS、コマンドインジェクションの可能性はないか？
- 機密情報（パスワード、トークン等）がログに出力されていないか？
- 認可チェック漏れはないか？

### パフォーマンス
- N+1クエリ等の明らかな非効率はないか？
- 不要なコピーや再計算はないか？
- ループ内で重い処理（I/O、API呼び出し等）をしていないか？

## 5. 一貫性

- 既存コードのパターン（ディレクトリ構造、ファイル命名、エラーハンドリング方式等）に従っているか？
- 新しいパターンを導入している場合、正当な理由があるか？
- インポート順序、フォーマットはプロジェクト規約に沿っているか？

## 差し戻し時

- 問題箇所をファイルパスと行番号で特定する
- 「なぜダメか」と「どう直すか」をセットで伝える
- 類似パターンが他にもないか確認を指示する（1箇所見つけたら他にもある可能性）
- 根本原因を追求する（表面的な修正ではなく、なぜそのコードを書いたかを問う）
